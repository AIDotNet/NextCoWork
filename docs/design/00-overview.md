# 00 · 总览与关键决策

## 1. 目标

1. **3.0 整个技术栈都用 C#(.NET 11;2026-11 从 .NET 10 升级)**:客户端、Agent、中继服务、插件运行时、构建和发布工具全部用 C# 实现,
   仓库里不再有 Node / TypeScript 运行时依赖。需要执行 JS 的地方(插件)一律用 [Jaunt](https://github.com/AIDotNet/Jaunt)。
   - 客户端:Avalonia 12(≥ 12.2.0,< 13)+ TKCode.Arc(锁定正式版 `1.3.1`,Avalonia 锁定 `12.2.0`),一套代码覆盖
     macOS / Windows / Linux / iOS / Android。浏览器(WASM)先不做,但架构上不堵死。
   - Agent:用 C# 重写,NativeAOT 发布为原生可执行文件 `ncw-agent`(旁边只带一个 e_sqlite3 原生库),不再内置 Node。
2. **Agent 运行时单独设计**:Agent 是一个独立的服务进程,对客户端类型无感知。
   桌面、手机、平板都是它的「控制端」,地位相同。3.0 只有两种部署:桌面内置和云端。
3. **3.0 只做 GUI**:所有用户操作(安装、配对、数据接管、诊断、回滚)都在图形界面里完成或自动完成。
4. **移动端可用**:手机上能看项目和会话、发消息、审批、看子代理、看 diff、停止运行,并且能收到推送。
5. **2.x 用户能平滑升级,并直接接管 2.x 数据**:已经装了 2.x 的用户通过现有的自动更新收到 3.0 并完成安装。
   不管 3.0 怎么装上的,首次启动都直接接管 2.x 的数据(会话、项目、供应商密钥;设备配对不迁移,因为协议是全新的),原地使用,不需要导出导入
   (见 [04 §4](04-update-install.md#4-数据接管直接接管-2x-数据))。
6. **界面重新设计**:不参考 2.x 的界面。采用「侧边栏 + 工作区 + 检查器」布局,侧边栏是可分组的项目树(2026-11 起取代最初的「项目栏 + 项目面板」两栏,见 03 §1)。
7. **提供云端 Agent**:没有自己电脑或服务器的用户(尤其是手机用户),可以在 nextco.work 上开一个托管的 Agent,
   体验和连接自有设备一致(见 [02 A6](02-agent.md#a6-云端-agent))。
8. **多设备执行与 SSH**:区分控制端、设备、执行环境三层。设备可以通过 SSH 在远程主机上执行工具,
   审批和工具卡片都标明「在哪执行」(见 [06](06-environments-ssh.md))。
9. **首次启动、登录和设置页重新设计**:浏览器登录后通过 `nextcowork://` 跳回应用;设置页按「本应用 / 设备 / 项目」三种作用域组织(见 [07](07-onboarding-settings.md))。
10. **模型目录自动更新**:Agent 定时从 `https://models.dev/api.json` 拉取模型数据(见 [02 A8](02-agent.md#a8-模型目录modelsdev-自动更新))。

## 2. 非目标(3.0 不做)

- 不在手机上运行 Agent。手机只做控制端(理由见 [02 A4](02-agent.md#a4-移动端约束))。
- **不做 CLI**:不做命令行控制端,不做插件 CLI;`ncw-agent` 只有给桌面端和云端编排用的启动参数,
  不提供面向用户的子命令(2.x 的 `takeover`、`diagnose`、`service install` 等)。
- **不做独立设备服务**(在 NAS 或服务器上单独部署 Agent),留到以后。3.0 客户端也连不上 2.x 的 TS 设备服务
  (升级时的处理见 [04 §2](04-update-install.md#2-升级路径经过桥接版本-29))。
- **不兼容 2.x 的设备协议和开放网关接口**:协议全新设计(见 [09](09-protocol.md)),2.x 的配对记录不迁移。
- 插件的 React 视图和自定义编辑器**暂不考虑**,不在 3.0 范围内。
- 内置浏览器、Office 编辑器依赖 WebView 方案,不保证在 3.0 GA 时对齐,
  分期计划见 [05 功能对齐矩阵](05-roadmap.md#2-功能对齐矩阵)。
- 2.x 的维护期暂不规划。
- **暂不考虑支付**:不做充值、钱包、计费;云端 Agent 只用配额限制;iOS 端因此也不涉及应用内购买。用量只做展示和费用估算。

## 3. 关键决策(ADR)

| # | 决策 | 理由 | 备选及否决原因 |
|---|---|---|---|
| D1 | 客户端和 Agent 分成两个进程,中间只走「设备协议」 | 移动端和云端只能远程连接。本机和远程走同一条路径,移动端就不需要额外开发;Agent 也能在关窗后继续运行 | 桌面端把 Agent 放进客户端进程:同语言后技术上可行,但本机和远程会变成两套逻辑,崩溃也会互相拖垮 |
| D2 | 桌面端安装包内置本机 Agent(sidecar),用回环地址加本机令牌连接 | 用户感知不到多了一个进程,开箱即用 | 让用户自己装设备服务:门槛太高 |
| D3 | **Agent 用 C#(.NET 10)重写**,NativeAOT 发布为原生可执行文件(外加 e_sqlite3 原生库)。2.x 的 TS 实现只作为参考实现和行为基准,不迁入本分支 | 一种语言;客户端和 Agent 共享领域模型、派生函数和协议类型;不再内置 Node,包更小,签名和公证更简单;云端也是同一个二进制 | 继续用 TS:两种语言、协议要双实现、Node sidecar 的签名和公证复杂。代价是重写的工作量(见 [01 §4](01-architecture.md#4-agent-移植策略)) |
| D4 | 协议**全新设计,不参考 2.x**(见 [09](09-protocol.md))。3.0 先做局域网直连:打开远程开关,用 `IP:端口` + 配对码连接;服务器中继(M6 已加)只新增承载、没有改协议。定义只有一个来源:`Ncw.Protocol` 程序集,客户端和 Agent 直接引用同一份类型;远程安全层用 TLS 1.3 双向认证,经中继时隧道内再跑 TLS;对外导出 JSON Schema / OpenAPI | 两端同一种语言,不需要代码生成,也不会漂移 | 维护单独的 schema 再生成代码:多一层,没有必要 |
| D5 | UI 用 TKCode.Arc,但业务视图只引用我们自己的薄封装 `Ncw.UI.*` | Arc 还是 preview 版本,封装一层可以隔离它的破坏性变更 | 业务视图直接用 Arc:升级时改动面太大 |
| D6 | MVVM 用 CommunityToolkit.Mvvm;序列化用 System.Text.Json 和 MessagePack 的源生成器;全栈不依赖反射 | iOS 和 Agent 都要 NativeAOT,桌面端也希望启动快 | ReactiveUI:较重,依赖反射的地方多 |
| D7 | 状态统一管理规则在 C# 里照搬(见 [01 §5](01-architecture.md#5-状态统一管理c-版)),而且派生函数由 Agent 和客户端共用 | 2.x 踩过的「四份状态互相打架」不能再来一次 | — |
| D8 | 2.x 自动更新到 3.0 时经过「桥接版本 2.9」:2.9 负责停掉 Run、做备份,并自己安装 3.0。数据接管不依赖 2.9(见 D20) | 不依赖 electron-updater 在各平台的内部行为(Squirrel 签名校验、NSIS 参数) | 直接把 3.0 安装包塞进 electron-updater 的 feed:macOS 上有签名校验风险,也没法在交接前整理数据 |
| D9 | 3.x 的自更新用 Velopack | .NET 生态里成熟的方案,三个桌面平台都支持,有增量包和通道,feed 是普通的静态 HTTP | 自研更新器:不划算 |
| D10 | 项目分组属于「用户布局」,通过账户配置同步;项目本身(工作区)的事实由 Agent 持有 | 分组可能跨设备(本机项目、云端项目、另一台电脑上的项目放在同一组),手机上也要看到同样的分组 | 分组存进某个 Agent:跨设备的项目无处安放 |
| D11 | 云端 Agent 和本机、自有设备用**同一个 ncw-agent 运行时、同一套协议**,nextco.work 只额外提供托管编排 | 客户端不需要为云端写第二套逻辑;云端和本机的行为一致 | 云端单独做一套多租户服务:等于维护两个 Agent |
| D12 | 3.0 起各平台正式签名:macOS 用 Developer ID 签名并公证,Windows 用 Authenticode(证书已具备) | Gatekeeper 和 SmartScreen 不再拦截;Velopack 在 macOS 上依赖签名 | 继续 ad-hoc 签名:3.x 自更新和首次打开都有问题 |
| D13 | C# Agent **直接读写 2.x 的 SQLite schema 和 `NCK1` 凭据格式**,在其上做增量迁移 | 升级时数据原地接管,不用导出导入 | 新库再导入:慢,还容易丢数据 |
| D14 | **JS 执行统一用 Jaunt**(纯托管、兼容 NativeAOT 的 JS 引擎;**M4 已评估并落地**:NuGet 1.0.3,NativeAOT 零警告且原生二进制实跑通过,见 [02 A7.1](02-agent.md#a71-jaunt-评估与实现m4))。2.x 插件的非 UI 部分(命令、Agent 工具、Skills)继续可用:插件 JS 在 Agent 进程内的 Jaunt 隔离 realm 里运行,有执行预算,宿主 API 按权限显式绑定(见 [02 A7](02-agent.md#a7-插件与-js-执行jaunt)) | 2.x 插件本来就跑在没有 Node API 的沙箱 iframe 里,只通过 RPC 调宿主,和 Jaunt 的模型一致;不引入 Node,AOT 下也能运行 | 插件全改成 MCP 服务器:破坏现有插件生态;ClearScript(V8):原生依赖重,iOS 不可用;Jint:不兼容 AOT,性能也不如 Jaunt |
| D15 | 浏览器工具**自己实现最小 CDP 客户端**(`Ncw.Agent.Browser`:ClientWebSocket + CDP JSON-RPC,Utf8JsonWriter / JsonDocument 手写),驱动设备上已有的 Chrome / Edge / Chromium;**不用 PuppeteerSharp,不用 Playwright**。原决定是 PuppeteerSharp,M4 实测不成立(见 [08.03 §14](08-agent-runtime/03-tools-permissions.md#14-实现注srcncwagentbrowser浏览器工具)):PuppeteerSharp 25.17.1 在 NativeAOT 下有 IL2026 / IL2075 / IL2090 / IL2091 / IL3000 / IL3050 共 11 类警告(CDP 连接的收发本身走反射 JSON),且自己 `Process.Start` 浏览器、绕过 `IExecutionEnvironment`、还要自己下载 Chromium | Playwright 自带 Node 驱动,和「全栈 C#」冲突;PuppeteerSharp 违反「AOT 零裁剪警告」和「进程只经执行环境」 | Playwright:要带一个 Node 进程;PuppeteerSharp:AOT 不可行,见左;自动下载 Chromium:引入网络与签名问题 |
| D16 | 中继服务、构建发布脚本也用 C# 重写:中继用 ASP.NET Core,构建发布脚本用 C# 控制台项目(`tools/Ncw.Build`;原计划的单文件程序装不下十几个文件、协议引用和单测,见 04 §7.1),只给开发和 CI 用,不对用户发布 | 一种语言、一套工具链,CI 只需要 .NET SDK | 保留 2.x 的 Node 脚本:仓库里会长期存在两套工具链 |
| D17 | 区分「控制端 / 设备 / 执行环境」三层。SSH 连接从设备发起;所有工具只通过 `IExecutionEnvironment` 访问文件和进程 | 同一个工具在本机、SSH、云端行为一致;手机控制时也清楚命令在哪执行 | 工具直接操作本地文件系统,SSH 另写一套:两套逻辑必然分歧 |
| D18 | 桌面登录用授权码 + PKCE,浏览器跳回**本机回环临时监听**(`http://127.0.0.1:{随机端口}/callback`,与 2.x 和线上后端一致);`nextcowork://` 只用于配对和打开链接;「改用登录码」走设备授权码(RFC 8628) | 线上后端(`ClientOAuth`)一直放行回环回调,已发布的 2.x 也这样登录,不依赖后端新版本;监听只绑 127.0.0.1、只收一次匹配的回调、登录结束即关,攻击面可控。后端仓库另已放行 `nextcowork://auth/callback`(留给手机和以后),部署前线上不认 | 自定义 scheme 回跳:任何程序都能注册同名 scheme,线上部署前也不被后端接受 |
| D19 | 模型目录由 Agent 定时从 models.dev 拉取,带条件请求、异常数据保护和内置快照兜底;价格自动采用,只用于估算 | 模型数据始终是新的,又不会因为一次坏数据出问题 | 每次发版内置一份:数据会过时 |
| D20 | 3.0 **直接接管** 2.x 数据,任何安装方式都可以;遗留的 safeStorage 凭据由 C# 按 Chromium `os_crypt` 格式直接解密 | 用户手动下载 3.0 也能无缝继续 | 只有经过 2.9 才能接管:手动安装的用户会丢数据 |
| D21 | 设置页是一个标签页,按「本应用 / 设备 / 项目」三种作用域组织,改动立即生效并可撤销 | 多设备之后,用户必须清楚自己改的是哪里的设置 | 沿用 2.x 的覆盖层设置页:看不出作用域 |

## 4. 术语

| 术语 | 含义 |
|---|---|
| **Agent 运行时 / ncw-agent** | C# 实现的服务进程,持有数据库、工作区、Git、终端和模型调用 |
| **控制端(Client)** | 连接 Agent 的图形界面程序:3.0 只有桌面端和手机端 |
| **执行环境(Environment)** | 工具真正执行、文件真正所在的地方:设备自身(`local`)或设备通过 SSH 连接的远程主机(`ssh`) |
| **设备(Device)** | 一个 Agent 运行时实例。桌面内置的那一个叫「本机」,nextco.work 托管的那一个叫「云端」 |
| **项目(Project)** | 某台设备上的一个工作区(目录)。界面上的一个项目图标对应一个 `(deviceId, workspaceId)` |
| **项目组(Group)** | 用户对项目的分组,纯布局数据 |
| **会话 / Run / 子代理 / 交互** | 沿用 2.x 的定义。交互指待处理的审批、提问等 |
| **设备协议** | 控制端和 Agent 之间的请求、订阅、交互协议,3.0 全新设计(见 [09](09-protocol.md)) |
| **参考实现** | `main` 分支上 2.x 的 TypeScript 代码,只用来对照行为、生成测试向量,不迁入本分支 |
