# 05 · 路线图与风险

## 1. 里程碑

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M0 设计评审** | 本目录全部文档 | §5 的待定问题都有结论 |
| **M1 骨架** | 解决方案、集中包管理、接入 Arc、`Ncw.UI.Controls` 薄封装、三栏 Shell 加 mock 数据、主题和中英文、项目栏和分组的交互 | 三个桌面平台都能跑起来;Avalonia.Headless 截图测试覆盖四个断点 |
| **M2 协议 SDK** | `protocol/` schema、C# 代码生成、编解码、E2E、配对、中转、RPC、事件续传;两边跑同一套黄金向量 | 3.0 桌面端能配对并控制**现有的 2.x 设备服务**,完成列出工作区、发消息、看流式回复、审批 |
| **M3 内置 Agent** | `agent/` 迁入(或依赖 npm 包)、sidecar 打包(Node 24 + node-pty 预编译)、本机通道、守护进程、数据根接管 | 全新安装开箱可用;拿一份 2.x 数据根接管成功并通过行数核对 |
| **M4 核心功能** | 会话和流式消息、交互、子代理(按状态规则来)、终端、文件、Git 和 Diff、模型和供应商、MCP、Skills、定时任务、设置 | 功能对齐矩阵里标「3.0」的条目全部完成;状态类单测全部通过 |
| **M5 移动端** | iOS 和 Android 宿主、`MobileShell`、扫码配对、活动收件箱、推送、附件上传 | 真机上走通「收到审批推送 → 打开 → 长按允许 → Run 继续」 |
| **M6 升级链路** | 2.9 桥接版(在 `main` 上开发)、Velopack、后端 v3 feed 和清单签名、3.x 自更新 | 三个桌面平台都完成「2.8 → 2.9 → 3.0 → 3.0.1」的端到端演练,数据完整 |
| **M7 扩展对齐** | 插件(用 WebView 承载)、内联可视化、内置浏览器、Office 文档 | 按矩阵分到 3.0 或 3.1 |
| **Beta → GA** | beta 通道灰度,收集崩溃和指标 | 崩溃率和升级成功率达标 |

M1 和 M2 可以并行。M6 里的 2.9 桥接版应该尽早启动,因为它需要先在 2.x 用户中铺开。

## 3. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| TKCode.Arc 还是 preview 版本 | API 可能变,也可能有 bug | 锁定版本;业务视图只用 `Ncw.UI.Controls` 封装;每次升级 Arc 都跑截图回归 |
| `TKCode.Arc.Mobile` 文档注明「尚未在真机上验证」 | 移动端组件可能不可用 | M1 就做一次真机 spike(iOS 和 Android 各一台)。不行的话,移动端改用 Arc 核心组件加自己写的导航 |
| Avalonia 上的 WebView 方案 | 影响插件视图、浏览器、可视化 | M1 做 spike,评估 Avalonia 12 的 WebView 控件和各平台原生 WebView 的嵌入方式 |
| sidecar 体积(Node 加原生模块) | 安装包大约多 60–90MB | 可以接受;后续评估 Node SEA 和按需下载 |
| 协议双语言实现出现漂移 | 两端不兼容 | 协议定义只有一个来源,外加黄金向量。CI 里两端互相连接做测试 |
| 2.x 用户升级失败 | 用户流失 | 桥接版先做完预检和数据整理;服务端灰度;回滚说明 |
| macOS 缺少 Developer ID | Velopack 和 Gatekeeper 都会出问题 | 见 Q3 |
| 2.x 维护期内 Agent 修复要双向同步 | 工作量 | `agent/UPSTREAM.md` 记录基线;维护期尽量短 |

## 4. 测试策略

- `Ncw.Core`:派生函数、Store 对账、状态单调、多设备断线。对应 2.x 的 subagent-view、subagent-monotonic、subagent-sync 这几组单测。
- `Ncw.Protocol`:黄金向量;断线、丢帧、重放(必须报错并断开连接,不能静默继续);游标续传。
- UI:Avalonia.Headless,覆盖四个断点和深浅两种主题的截图回归。
- 端到端:真实的 ncw-agent 加 3.0 客户端,跑冒烟脚本(沿用 2.x 的 `agent-smoke` 思路)。
- 升级演练:在三个平台的虚拟机里跑 2.8 → 2.9 → 3.0 → 3.0.1,前后对比数据库行数和凭据是否可以解密。
